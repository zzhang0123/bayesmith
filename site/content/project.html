Roadmap

The normative design defines nine stages. The status column is read from the tree: a stage counts as delivered when its modules, tests and a dated close-out record exist, and open items are named rather than folded into a verdict.

The design document is the source for the goals; this page is the source for what exists. Where they disagree, the tree is right and this row is stale. See research records for the close-out documents and principles and verification for how each stage's claims are checked.

Compatibility policy

The baseline preserves the supported public APIs and artifact schemas. Experimental primitives retain the limits listed above. Public breaking changes need migration instructions; correcting a numerically wrong answer can still break a consumer that relied on it and must be documented.

The deprecated bayesmith.evidence aliases migrate to bayesmith.marginal. The old namespace must never be reused for different task-level evidence semantics. Backend-native objects have weaker portability than bayesmith's typed artifacts.

Release acceptance sequence

  1. Resolve architecture and API findings, then have independent reviewers reassess the final changes.
  2. Run source fast/full checks, lint, Linux wheel and extracted-sdist verification; record commands, exit codes, skips and numerical stack.
  3. Have the downstream consumer run its suite against the candidate revision. A previous green report is not a verification of a new candidate.
  4. Build this site strictly, execute tutorials, inspect mobile and keyboard behavior, and verify API coverage.
  5. Align version, changelog, migration notes and artifact compatibility; preserve the tested candidate manifest.
  6. Publication requires a separate release decision.

These are acceptance requirements, not claims that this documentation build has executed them. The existing design's 1.0 milestone has additional ecosystem and workflow requirements; stabilizing a 0.x release does not silently satisfy them.
