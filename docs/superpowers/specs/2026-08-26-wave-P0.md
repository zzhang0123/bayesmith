## 三、发布当天,索引有三个说法,只有一个是对的

绿的 publish workflow 是**记录**,不是索引。分别问了三处,同一分钟内:

| 问谁 | 答案 | 是什么 |
|---|---|---|
| `pypi.org/pypi/bayesmith/json` | 只有 **0.1.0** | JSON API 的缓存,滞后 |
| `pypi.org/simple/bayesmith/` | 0.1.0 **与 0.2.0**(whl + tar.gz) | pip 真正解析的那张表 |
| `uv pip install 'bayesmith>=0.2'` | 「unsatisfiable」 | uv **本地**索引缓存 |

三个说法里两个说「没发布」,而发布确实成功了。这与两份 CLAUDE.md 反复记的
是同一族陷阱:**一个分不清「不存在」与「这次没真去问」的结果**。`--refresh`
之后 uv 立刻装上 `bayesmith==0.2.0`,JSON API 几分钟后也追上了。

**教训写成可执行的一句**:发布后要证明 floor 合规,问 `/simple/`,或者用
`--refresh` 真解析一次;单问 JSON API 会读成「发布没成功」,而那正是会让人
去重推 tag 的假象——tag 已经不可变,重推只会更糟。

最强的那次证明是真解析:在一次性 venv 里 `uv pip install 'bayesmith>=0.2'
--no-deps --refresh` → `bayesmith==0.2.0`,并在装出来的**轮子里**核实
floor 所指的两个模块确实在:`dispatch/factor.py` 有 `def first_fit`,
`exact/loglinear.py:173` 有 `y = jnp.log(observed) + fractional**2 / 2.0`。
源码树跑绿而包里少一个模块是真事,所以查的是安装后的文件。
