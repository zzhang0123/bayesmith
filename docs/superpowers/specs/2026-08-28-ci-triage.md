## 〇、为什么这一页不是「CI 抖动,放宽了事」

交接页把 CI 列为**下一位第一件事**,并给了判别法
(`2026-08-27-ci-flat-chain.md` §三):**问这条断言钉的是大效应还是小差值**。

六条过下来,结论**不是**「都是抖动」:

| # | 失败 | 判别 | 处置 |
|---|---|---|---|
| 1 | `Block 0 does not come from epoch 'collinear'` | **大效应**(2e1 对 2e-6 带) | **真缺陷**,守卫比较了一个非不变量 |
| 2 | `ratios["t21_depth"] > 3*ratios["running"]` | 小差值(两个量都 ~1e-11) | 命题本身不成立,换成不变性 |
| 3–5 | 三条壁钟预算 | 小差值(硬件) | 加机器标定因子,一个数字都不放宽 |
| 6 | `A13 ... 336 Hz` 文案相等 | 小差值(半个 ulp) | 并入本模块**已有**的派生器 |
| 7 | `node_modules/.bin/tsc` 找不到 | 环境 | Coverage job 漏了 Suite 的三步 |

**共同教训在最后一节**,因为它不是关于这六条中的任何一条。

## 一、第 1 条是真缺陷,而且是最反直觉的一种

`ChainMemory.__init__` 用 `_quadratic_form` 的三个系数把每个存储块与档案指名的
epoch 对齐。那个函数的 docstring 说这三个是「一个存储块与它来自的 epoch 所共有
的东西,也是它们共有的全部」。**前两个是。第三个不是。**

`_square_block` 经 `combine(null, info)` 存储,而 `combine` 会重新三角化:x 的
任何二次型都表达不了的那部分残差成为角落 `rho`,它离开 `target`、以 `-rho^2/2`
付进 `offset`。于是 `z.z` 掉 `rho^2`,`offset` 掉 `rho^2/2`,而它们的**和**掉
**`1.5 * rho^2`**。

```
                          found (存储块)   expected (档案)   差
z.z + offset              6.406195725      28.338457405     21.932    <- 守卫比的
offset - z.z/2          -12.674938872     -12.674938866      5.6e-09  <- 真的不变量
```

`21.932 = 1.5 * 14.6215`,而 `14.6215` 就是 `rho^2`——从 target 侧算与从 offset
侧算,两者相符到 1.1e-8。

**它为什么以平台差异的形式浮出。** 精确共线的设计,其 QR 有一个零主元,而
**LAPACK 把那个零放在哪一行**因机器而异:

* darwin/arm64:第 1 列约到 `1.36e-16`,零方向**留在保留块内**,角落为空,
  `rho = 0`,错的公式与对的公式相等;
* linux/x86-64:精确约到 `0`,质量移进角落,`rho^2 = 14.62`,两个公式相差 21.93。

**块在两台机器上都是对的。** 守卫在其中一台上抛
`StateValidationError`,内容是「这条链被打乱了」——**一次对正确数据发出的数据
完整性指控**,而且只在没人开发的那台机器上复现。

**修法与它的守卫。** `_quadratic_form` 的第三个系数改为
`offset - 0.5 * (target @ target)`,并补
`tests/evidence/test_chain_block_invariants.py`(12 条)。三个 fixture 用**手搭的
`SqrtInfo`** 把非空角落造出来,`rho^2` 恰为 **25 / 16 / 0**——**不依赖平台**,因为
一个角落必须承载的残差是**算术**的性质而不是 LAPACK 的。第一个 class 就是
`TestTheFixturesReachTheStateTheyClaimTo`:先证明 fixture 到得了那个状态,否则
底下每一条都是空转,**而那正是这个缺陷活下来的方式**。

## 二、第 2 条:断言的是一条不成立的普遍命题

`test_the_ratio_is_marginalised_and_a_raw_gradient_amplitude_names_the_wrong_culprit`
在**种子基**上断言排序反转(原始梯度说 `running` 差 9.4 倍,边缘化比值说
`t21_depth` 差 4.0 倍)。那里两个量都是 **~5e-12**,而**同一文件里相邻测试的注释
已经写着**:「这是 1e-11 量级的 bias-over-sigma,也就是一个已经与零无法区分的
相干误差,其绝对大小由算术在哪里舍入决定,而不是由这次战役决定。」

在偏差**真实**的 fixture 上扫描(`min |mrg|` 在 5e-9 到 4e-5 之间):

```
n_basis  key   raw r/t   mrg t/r   min |mrg|
      5   50      3.09      2.68   3.468e-06   <- 反转
      5    7      7.33      0.81   7.183e-07   <- 两者都指 running
      5  123      0.56      9.47   2.694e-06   <- 两者都指 t21_depth
      6    7     57.76      0.59   1.025e-08   <- 两者都指 running
```

**反转随随机 key 变号。那不是方法的性质。**

换成真正成立的、而且正是这条测试想说的那件事:**边缘化比值对参数化不变,原始
梯度不变**。把某个 latent 缩放 `1e6`(同一个模型,不同单位),`F^-1 g` 与
`sqrt(diag(F^-1))` 同吃一个因子而相消——报告的四个比值**一个不动**;原始梯度则
整体改口,**它先前叫得最轻的那一维成了最重的一维**。断言写成 **argmax 翻转**,
不是余量,因为余量正是这个文件已经栽过两次的地方。

另补一条把公式本身钉在手算上的测试(`|F^-1 g| / sigma`,`rel=1e-9`),跑在
`min |mrg| > 1e-6` 的 fixture 上。

## 三、第 3–5 条:三个数字一个都没放宽

三条绝对壁钟预算,**刻意收紧**,各自配着变异标定表:

| 测试 | 干净数 | 界 | 余量 | CI 实测 |
|---|---|---|---|---|
| `axes` pass | 0.0138 ms | 0.09 ms | x6 | 0.106 ms |
| A35 自身的 walk | 0.74 ms | 2 ms | x2.6 | 2.74 ms |
| preflight pass | — | 0.05 s | 「余量」 | 0.0512 s |

三份 docstring 都把余量的**取值理由**写了下来(「六而不是十:六是仍然死于一次
干净的 x10 减速的最大余量」)。runner 每次操作约慢**四倍**,余量整个被吃掉。

放宽这三个数字就是把它们写来抵抗的那件事撤掉。改为在
`tests/config/inflight_helpers.py` 加 `machine_factor()`:一段**纯 CPU**、与各
pass 同类工作(dict 迭代、`__slots__` 属性访问、分支、`len`、小 f-string)的参照
负载,除以本机标定值 `CALIBRATION_MS = 0.090`(十二次独立 best-of-30 的中位数,
0.084–0.092,离散 8.9%)。

**每一张标定表都还成立**,因为表里每一行都与干净数随机器同比例移动;而代码本身
慢 10 倍**仍然红**,因为参照不跟着它动。不设上限:因子到 20 意味着这些界已经不再
判别任何东西,那时该有一条红测试把这句话说出来,而不是一个静默的地板。

## 四、第 6 条:策略早就有了,漏了一处

`A13_JUST_UNDER_THE_FLOOR_MESSAGE` 把 `336 Hz` 写死在文案里。该 band 的真实
间距是 **333.33 Hz**,而 float32 在 7e7 处的 **ulp 恰好是 8 Hz**:

```
float32 频率:  70000000.0   70000336.0   70000664.0   70001000.0
gaps        :        336          328          336
```

三个 gap 的中位数落在 328 还是 336,由 `linspace` 往哪边舍入决定。

**本模块早已诊断过这件事**——`_assert_equals` 上方的注释逐字写着「Measured 336
on arm64 macOS and 328 on x86_64 Linux: two correct readings of an axis that
cannot say 333」,并建好了 `assert_a13_narrow` / `assert_a13_wide` 两个派生器,
结论是「the digit is the platform's」。

**这一条是唯一没有被改造的断言。** 于是它红而兄弟们全绿——读起来像检查坏了,而
不是像一条策略漏了一处。

并入同一个派生器:`a13_narrow_message` 加一个 `width` 参数(**一个生成器,不是
第二份拼写**),新增 `assert_a13_just_under_the_floor` 处理这条消息里的**两个**
平台数字(间距,以及 `floor * (1 - 2*rtol)` 这个把间距带进第二个槽的宽度)。

并补一条**扫描本模块命名空间**的守卫:任何 upper-case 字符串常量都不得把
channel spacing 写成字面量。它自己也有一个兄弟,因为它读的是命名空间,一个不再
匹配的正则会报告「本模块很干净」而不是失败。

## 五、第 7 条:同一个形状

`Coverage (serial)` 跑的是**同一套测试**,却没有 Suite 那三步 Node 配置。
`8ed385f` 的标题正是「the toolchain CI never installed」——它只给 Suite 加了。

补齐三步(setup-node、`npm ci`、`playwright install chromium`),理由与 Suite 里
那段注释一字不改地适用:前端是本项目的一部分,工具链属于 CI,而不是让守卫学会
站下。

## 六、D50:`reweight_tol` 那条守卫用的是一个不存在的 fixture

见登记簿 D50。要点:它上一次**已经被硬化过一轮**(不再写死步数,改成搜索一个
「还在动」的步长),而这次搜索区间内每个步数都精确收敛,测试用它自己的诊断消息
失败——**「pick a fixture whose reweighting is still moving」**。

实测:这个家族里**没有那样的 fixture**。`delta` 在 1 次重加权时是 `inf`、在 ≥2 次
时是舍入量(4.7684e-07 / 8.9391e-07 / 恰好 0.0 / 加了散射也是 1.4304e-06),
**中间没有稳定值**。一个「低于 delta」的容差在精确收敛的机器上必须低于零。

转发本来就是这条测试自称要立的论点,于是直接钉转发。变异验证:从
`_GLS_KNOB_SPECS` 删掉 `reweight_tol` 一行,该测试**逐名击杀**。

## 六点五、变异

五行协议,规则 (0) 两半都守。击杀 = 退出码**恰为 1** 且登记的测试在红名单里。

| # | 变异 | 判决 | 由谁杀 |
|---|---|---|---|
| C1 | `_quadratic_form` 第三项改回 `z.z + offset`(即把缺陷放回去) | KILLED | `test_every_coefficient_survives_being_stored`(+ 4 条) |
| C2 | 那一半的符号:`offset + 0.5*z.z` | KILLED | 同上 |
| C3 | 那个因子:`offset - 1.0*z.z` | KILLED | 同上 |
| T1 | **测试变异**:把 `ZERO_ROW` 的零行改成非零(角落变空) | KILLED | `test_the_rank_deficient_fixtures_leave_a_corner` |
| T2 | **测试变异**:单位重标度从 `1e6` 改成 `1.0` | KILLED | `test_the_marginalised_ratio_is_invariant_to_units_and_the_raw_gradient_is_not` |

**T1 与 T2 是这一批真正要问的两条。** T1 把 fixture 退回到「角落为空」——也就是
**每一个既有 fixture 所处的状态**,即这个缺陷赖以存活的状态;可达性 class 抓住了它。
T2 把重标度退成恒等,于是 argmax 不再翻转;那条断言读的确实是翻转,不是任何重标度
都能满足的东西。

变异集前后基线各一次绿。恢复路径**只含变异点自己的三个文件**,不宽于它们。

## 七、共同教训,它不是关于这六条中的任何一条

**六条里五条的根因是同一件事:一条规则、一次修复、一个策略,只被应用到了它被
发现的那一处。**

* A13 的间距策略建好了派生器,**漏了一条断言**;
* Node 工具链的修复提交标题就叫「CI never installed」,**漏了一个 job**;
* `reweight_tol` 的可移植化做过一轮,**漏了这条测试**;
* 壁钟预算的三份 docstring 各自独立地把余量算得很仔细,**没有一份问过这台机器
  是不是那台机器**;
* `_quadratic_form` 的第三个系数从来没有被任何 fixture 在 `rho != 0` 处问过。

判别法本身是对的。它只在**有人把它拿到每一处**时起作用,而「每一处」不是一个
会自己出现的清单——所以本批次给其中两处补的是**扫描式守卫**(命名空间扫描、
fixture 到达性 class),而不是又一条正确的断言。
