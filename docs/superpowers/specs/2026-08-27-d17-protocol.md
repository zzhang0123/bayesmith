## 〇、这一步在裁决什么,以及不在裁决什么

D17 问的是**分区/对数发现探针住哪边**:rheplicant 的探针读
`Pipeline` + `ParameterSpace`,bayesmith 的读 `Graph`。owner 于 2026-08-26

协议本身写在计划里:同一组 fixture 双跑 diff,**逐例一致才换**,不一致的逐个
上登记簿。本页是那次运行。

**着色循环早已是共用的。** `rheplicant.inference.partition` 导入
`bayesmith.dispatch.factor.first_fit`,把成对判决变成分组的规则只有一份实现。
所以本协议比的**不是分区逻辑,是喂给它的探针**——这正是 D17 的题目。

## 一、fixture 集:一个函数,两侧各包一层

每个 fixture 的预测**只写一次**,是一个 latent 字典到数组的普通 jax 函数;
rheplicant 侧把它包进一个 `AbstractOperator`,bayesmith 侧把它包进一个 `det`
节点。**把模型写两遍,正是一个比对悄悄变成「比两个不同模型」的方式**——本
程序上一批刚付过这笔学费:一个图 fixture 漏了加性 offset,与手造孪生体差
0.16,读起来完全像求解器 bug。

判决被归一化成 `(种类, 排序后的名字)` 的排序元组,两套词汇映射为
`exact | log | gradient`:

    rheplicant  conjugate | log_conjugate | gradient
    bayesmith   gcr       | log-gcr       | nuts

覆盖计划点名的三条轴:**极端 f**(0.004 / 0.06 / 0.3)、**边界仿射**、
**D16 第五轴的亮暗混合模型**。

## 三、第一族(例 4、6):rheplicant 的分区探针**看不见噪声**

这一族**不是两个包对同一个问题有不同意见**。实测:rheplicant 问的是同一批
问题、用的是**同一个常数**,只是问得**晚**——问在 `to_log_space` 里,而那里
拿得到噪声模型,`auto_blocks` 拿不到(它的签名只有 space / pipeline / state)。

探针的求解期交叉测量(同一页脚本的第二节):

| 噪声 | rheplicant `to_log_space` |
|---|---|
| 加性(`HomoscedasticNoise`) | **REFUSED** — 「需要乘性噪声模型…」 |
| 乘性 f=0.004 | ACCEPTED |
| 乘性 f=0.06(上限本身) | ACCEPTED |
| 乘性 f=0.3 | **REFUSED** — 「f = 0.3,高于 0.06…」 |

`FIRST_ORDER_MAX_FRACTIONAL` 两边都是 **0.06**,同一个数。所以两侧的**判据
一致**,分歧全在**判据被应用的时机**。

**这一族的后果不止是「谁先问」。** 实测链条:

```
auto_blocks(加性噪声模型)  ->  {('g',): 'log_conjugate'}
to_log_space(同一模型, HomoscedasticNoise)  ->  ParameterSpaceError
```

也就是说,`auto_blocks` **产出了一个它自己的求解器会拒绝的分区**。而
`partition.py` 的模块 docstring 恰好写着这件事该被避免:

> 「Grouping them wrongly is not a silent error……But a refusal is not a
> partition, and producing one is this module's whole job.」

按 rheplicant 自己的教条,这是一个缺口而不是风格差异。bayesmith 的探针没有
它,因为它的 log 通道在分区期就读噪声——加性噪声被记为 `noise_additive`,
f 超限被记为 `fractional_too_large`(两者都是 G11 刚落地的 `reason` 字段)。

**语义上,两侧的「log-linear」问的本就是两个问题**:rheplicant 的
`check_log_linearity` 问「`log(prediction)` 对这个 latent 是否仿射」——只关
预测;bayesmith 的 log 通道问「取对数是否**简化这个似然**」——必须读噪声,
因为对已经是加性的噪声取对数,得到的是**另一个**似然,而不是同一个的简化。
两个问题都合理,但只有后者能单独决定分区。

## 四、第二族(例 7、8):这是 **D16** 的两条轴,不是 D17 的新问题

- **例 7 `boundary_affine`**:预测是 `signal + 1e-7 * signal**2`。两侧都在
  「1000 × 先验宽度」这一档探,但**锚点不同**(D16 第一轴:rheplicant 取
  `max|init|`,bayesmith 取先验宽度),所以探到的**不是同一个点**,自然给出
  不同判决。bayesmith 的拒绝理由逐字点名了那一档:「too large at [1000.0]
  times each latent's declared prior width」。
- **例 8 `bright_and_faint`**:一个 1e8 量级的线性叶子旁边放一个 1e-2 量级
  带二次项的暗叶子。bayesmith **逐元素**判据抓到了暗叶子(拒绝理由:
  「[1.0, 1000.0] … per element」),rheplicant 的**整输出 max** 把它稀释掉,
  于是把 u 和 v 放进同一个 exact 块。**这正是 D16 第五轴,计划已经预言过**:
  「bayesmith 实测过整域 max 放行逐元素拒绝的假声明」。

**因此 D17 在这条轴上是 D16 的下游。** 先定 D16(探针判据的家与聚合粒度),
例 7、8 会跟着定;反过来先定 D17 只会把同一个决定做两遍。

### 第一族的实现,以及裁决没说的那一半

裁决说了「传噪声就检查」,没说**不传时怎样**——而那正决定缺陷是否真的关上:
今天全部 12 个调用点都不传。按能关上它的读法实现:

- **传了 `noise=`**:两条拒绝在分区期生效,被拒的 latent 落进梯度块。
- **没传**:探针照跑,但**不声明任何 log 块**,并发
  `UncheckedLogRouteWarning` 点名那些「仅凭预测就够格」的 latent。
  保守(梯度永远是个成立的判决,不会给出错答案)且**不静默**——否则这次修的
  缺陷会从「错的」变成「悄悄的」,那更糟。

**判据被抽成了一个谓词**,而不是抄第二遍:`loglinear.log_route_refusal(noise)`
返回 `"noise_additive"` / `"fractional_too_large"` / `None`,分区期读它、
`to_log_space` 也读它(后者只负责把同一个判决**措辞**成完整的拒绝)。抄第二遍
的话,这个缺陷会换个形状回来。词汇表刻意与 bayesmith 的
`NOT_LOG_LINEAR_REASONS` 同名。

**防漂移守卫**:`test_the_two_consumers_of_the_predicate_cannot_disagree`
逐个噪声断言「分区期是否拒绝」⟺「求解期是否抛出」——五个噪声模型,含上限
本身。两个消费者今天共用一个函数,但那是实现;这条测的是**性质**。

## 六、一个把第一次运行整个读反了的自制缺陷

第一次跑,协议报 **1/6 一致**,而且看起来煞有介事:分组正确、种类全是
`gradient`。原因在我的归一化里——

```python
{"conjugate": "exact", "log_conjugate": "log"}.get(block.engine, "gradient")
```

rheplicant 的 `Block.engine` 对**推导出来的**块是 `None`(引擎由
`SamplingPlan` 推导,不写在 Block 上),于是每一个推导块都落进 `.get` 的默认
分支,被读成 gradient。这是两份 CLAUDE.md 反复记的同一族陷阱:**一个分不清
「是 X」与「这次查询根本没发生」的结果**——而且这次它没有报错,只是给出了一
个完整、自洽、全错的表。

修法是问 `SamplingPlan(space, *blocks).engines`,并把两张词汇表写成**没有默认
分支的显式字典**:未知的引擎名现在会 `KeyError`,而不是被静默归为 gradient。

记在这里,是因为这个协议的产物是一张**判决表**,而一张判决表最危险的失败模式
不是跑不出来,是跑出一张读起来很合理的错表。
