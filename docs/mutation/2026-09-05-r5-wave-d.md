## Method note: a wake-up condition is a check, and the same disease reaches it

Three ways of waiting for one mutation driver were armed during this wave, and
**two of the three could not distinguish "the work finished" from "the thing I
was watching stopped existing for another reason."** Both look like patience.

| waiter | what it watched | why it cannot answer |
|---|---|---|
| `while pgrep -f "mutate2.py"; do sleep 30; done` | a process PATTERN | the waiting shell's own command line contains `mutate2.py`, so `pgrep -f` matches the waiter. It waits for itself. |
| `until grep -q "KILLED=" out` | a CONTENT marker | the driver's stdout is block-buffered to a redirect, so the marker lands only on a clean exit. A signal loses the buffer and the marker never appears. |
| `while kill -0 <pid>` | the PID itself | fires however the process leaves the table — clean exit, crash, or kill. |

The same trap ran the other way earlier: a status check
`pgrep -f "mutate2.py" && echo RUNNING || echo "NOT RUNNING"` reported RUNNING
**correctly, by luck** — the pattern matched the checking shell, so it would have
said RUNNING with no driver at all. Settled with
`ps -o pid,ppid,etime,stat -p 29594`, which takes a pid and no pattern.

Two rules, which are one rule: **wait on the pid, not on a pattern or a marker**,
and **run a driver whose output you intend to read under `python -u`** — a
buffered log is a result that does not exist until the process agrees to exit.

This is the fourth family of `CLAUDE.md`'s founding disease in this batch, after
the zsh glob, the ruff cache and the spelling guards, and the first that is
about a check's own TERMINATION rather than its subject.
